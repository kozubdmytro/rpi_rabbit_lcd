## Текущее состояние после самостоятельной проверки, 2026-11-12

**По последней просьбе пользователя привязка полностью сброшена.** RESET для
0x0101 подтверждён нодой; запись и индивидуальный ключ удалены с хаба.
В dev_keys остался только собственный 0001, записей нод в gateway.conf — 0.
COM5 подтвердил `NOT CONNECTED (not provisioned)`, реклама хаба активна.
Не добавлять ноду автоматически: пользователь будет проверять сам.

До этого сброса C3 была привязана: UUID `aabb9888e0d18b060000000000000000`,
адрес **0x0101**, показания 24 °C / 46 %. Адрес 0x0100 ранее забыт;
NVS ноды очищался через COM5 по указанию пользователя. Адреса не переиспользованы.
Одна автоматическая SCAN/BIND-попытка через текущий Gateway с включённым
GATT и его паузой завершилась COMPLETE за 7 с. Ограничение попытки — 30 с.
Физический телефон в этой автоматической попытке подключён не был.

После этого доработан `src/mesh/bluez.cpp`: при паузе GATT перед настройкой
закрывается старая частная D-Bus-сессия и выполняется Attach с новым владельцем.
Объект Gateway, принятая команда, request ID, boot ID и ключи сохраняются;
привязка начинается после повторного Attach. На запуске с сохранённой нодой
подтверждены повторный Attach, завершение настройки и возврат рекламы.

Дополнительно исходящие Mesh-сообщения к удалённым нодам ждут снятия рекламы
телефона. Возобновление рекламы отложено на 500 мс после отправки, чтобы
рекламный слот не вытеснял REPORT ACK; уже установленный телефонный линк
ради этих коротких окон не разрывается. Очередь обрабатывается Bluetooth worker.
После установки по SSH COM5 подтвердил:
`Provisioner: CONNECTED | transfer acknowledged; sleeping 12 s`.
Протоколы и прошивка C3 не менялись. Новую привязку после последней доработки
и полный сценарий с физическим телефоном не проверяли; дефект контроллера
0x2005 нельзя объявлять полностью устранённым. Телефон по ADB недоступен,
у ПК не обнаружен Bluetooth-адаптер для воспроизведения его соединения.

## Ранее выполненные этапы

## Пауза GATT при настройке нод, 2026-11-12 — проверка привязки отложена

Для BIND, RETRY_CONFIG и обычной настройки сохранённых нод после запуска
добавлен handoff в `src/mesh/bluez.cpp` и gate в `src/mesh/gateway.cpp`.
После принятия команды worker оставляет 250 мс на ответ ATT, приостанавливает
рекламу, отключает телефон и снимает GATT-приложение с регистрации BlueZ.
Provisioning/configuration не начинается до завершения этих операций.
Ожидание handoff ограничено 8 секундами; при сбое используется обычное
восстановление процесса, без старта привязки и без удаления ключей.

После завершения работы backend (включая его завершение после ошибки)
GATT и реклама восстанавливаются. Результат A00B/request ID сохраняется в
текущем процессе; повторный BIND с тем же ID не запускает новую привязку.
При переподключении CCC и замороженный инвентарь очищаются как раньше:
телефон подписывается заново, читает статус и выполняет CAPTURE.
Автоматическое переподключение и отображение прогресса зависят от клиента
телефона: его код в этом проекте не менялся. RESET/FORGET, UUID, payload,
ошибки ATT и сроки Mesh-транзакций не менялись.
До пользовательской проверки нельзя считать добавление через телефон
подтверждённым. Ноду 0x0100 повторно не привязывать и не сбрасывать.
Сборка и установка по SSH завершены. При штатном запуске службы в журнале
подтверждены pause/restore GATT, после восстановления ActiveInstances=1,
служба active без автоматических перезапусков. Новая привязка не запускалась.

## Восстановление запуска после отключения питания, 2026-11-12

После холодного запуска Mesh-служба получила имя D-Bus раньше готовности
контроллера/API; Attach завершился `No matching method found`. Bluetooth worker
остановился, но процесс экрана продолжал работать без GATT-рекламы.
`deploy/fix-bluetooth-startup.sh` установлен на Pi: Mesh ждёт включения hci0,
приложение — наличия метода Network1.Attach. Файлы сохраняются через fsync.
При последующей фатальной ошибке gateway приложение теперь завершится с ошибкой,
чтобы systemd автоматически его перезапустил. Новая привязка не выполнялась.
После обновления бинарника получены 24 °C / 47 % от 0x0100;
реклама SRLAB_THPS_MAIN / 00A0 активна. Холодный запуск ещё не проверен.

Дата: 2026-11-12. Пользователь разрешил одну прямую попытку через SSH,
ограниченную 30 секундами. **Привязка без телефона успешна; добавление при
одновременном подключении телефона остаётся нерешённым.**

  использовала существующие `Gateway` и BlueZ backend, без регистрации GATT
  телефона; команды SCAN/BIND выполнялись в том же Bluetooth worker.

  Диагностика завершилась раньше ограничения 30 секунд.

Нода теперь уже привязана: повторно добавлять или стирать её не нужно.

- C3 с BME280 обнаруживается, UUID `aabb9888e0d18b060000000000000000`.
- Телефон передаёт команду BIND; Pi переходит в PROVISIONING.
- В записи btmon найдено 87 исходящих MGMT Mesh Send с PB-ADV Link Open

## Вывод и границы уверенности

Подтверждены сбой операции контроллера Pi и незавершённый начальный PB-ADV
обмен. Основная гипотеза — конфликт операций сканирования/рекламы/передачи
при совместном использовании встроенного Bluetooth телефоном и Mesh.
Для BlueZ 5.82 и Raspberry Pi описаны сходные ошибки:

- https://github.com/bluez/bluez/issues/2337
- https://github.com/bluez/bluez/issues/1950

Эти отчёты не доказывают, что подходит конкретный workaround. Точная правка
и её эффективность на SRLAB пока не установлены. Нельзя объявлять C3 или
телефон полностью исключёнными из причин: активное соединение телефона может
провоцировать конфликт общего контроллера. Приложение телефона, однако,
доставляет команду добавления до Pi.

## Программный обход — unverified

Правка `deploy/bluez-5.82-mesh-scan-tx.patch` меняет только MGMT-передачу
в `bluetooth-meshd` версии 5.82:

- Перед каждым Mesh Send ставит в очередь остановку Mesh-приёма, затем
  передачу, затем восстановление прежних фильтров и параметров сканирования.
- MGMT-клиент BlueZ выполняет команды последовательно. В Linux 6.18 настройка
  передачи и восстановление приёма проходят через одну HCI-очередь: смена
  случайного адреса выполняется до возобновления Mesh-сканирования.
- Приём возобновляется после настройки передачи, без ожидания её окончания,
  чтобы не пропустить Link Ack. Следующая передача ждёт события завершения
  предыдущей; иначе ядро могло бы отложить её до уже включённого сканирования.
- Восстановление приёма запрашивается также при отказе Mesh Send. Ошибки
  управления приёмником записываются в журнал. Повторные передачи не расходуют
  свой счётчик при ожидании; callback больше не хранит освобождаемый tx-пакет.

Это обход предполагаемого конфликта, а не доказанное исправление прошивки
контроллера. Дополнительное сканирование, запрошенное другими процессами,
может мешать обходу; задержки и надёжность PB-ADV ещё не проверены.
Форматы GATT/Mesh, тайм-ауты управления нодами и исходники ESP32 не менялись.

Сборка: `deploy/build-mesh-workaround.sh`, только цель `mesh/bluetooth-meshd`.
Скрипт использует исходники и все патчи установленного пакета Raspberry Pi OS
`5.82-1.1+rpt2`; архивы закреплены SHA-256 из его `.dsc`.
Установка использует отдельный бинарник
`/usr/local/libexec/bluetooth/bluetooth-meshd-srlab` и drop-in
`/etc/systemd/system/bluetooth-mesh.service.d/srlab-scan-tx.conf`.
Пакетный бинарник, Wi-Fi и хранилища Mesh не заменяются.

На SRLAB сборка завершилась успешно; бинарник и drop-in установлены по SSH.
Команды перезапуска `bluetooth-mesh.service` и `smartrabbit-test.service`
завершились успешно. После установки журнал, статус служб, эфир и привязка
не проверялись по просьбе пользователя. Добавлены только библиотеки для
сборки: существующие системные пакеты не обновлялись и не удалялись.

При установке обхода проверки не запускались. Позже пользователь отдельно
разрешил прямой запрос и короткую проверку; её результат записан выше.
Стабильность и одновременная работа телефона/Mesh всё ещё не подтверждены.

Откат при необходимости: в указанном drop-in вернуть `ExecStart` на
`/usr/libexec/bluetooth/bluetooth-meshd`, выполнить `systemctl daemon-reload`,
перезапустить Mesh-службу и приложение. Ключи не удалять и сеть не создавать.

Дополнительно при осмотре рекламы обнаружено отсутствие явного свойства
`Discoverable` в `LEAdvertisement1`; это пока не исправлялось и не доказано
причиной проблем поиска телефоном. При осмотре BlueZ показывал активную рекламу
с именем `SRLAB_THPS_MAIN` и UUID сервиса `00A0`.

## Ограничения пользователя

Не запускать широкие тесты и многочисленные проверки. Сборка и установка
через SSH ранее разрешены; новые сбросы, стирание Mesh-ключей и перепрошивка
нод без отдельного указания не разрешены. Пароли в этот файл не записывать.
Основные сведения о проекте — в `BLE_SETUP.md` и `BLE_MIGRATION.md`.
